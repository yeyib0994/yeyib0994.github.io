# JVM 核心原理与调优实战指南

Java 能"一次编写，到处运行"，靠的就是 JVM（Java Virtual Machine）。它不只是个运行时容器，更是 Java 生态性能与稳定性的基石。理解 JVM，写出的代码才经得起高并发、大流量的考验；会调优，线上出问题才不会只会重启。

这篇文章用十分钟，把 JVM 的核心原理和调优实战讲清楚。

## 一、JVM 内存模型：对象都去哪了

JVM 在启动时会向操作系统申请一大块内存，然后划分成不同区域，各司其职。

- **堆（Heap）**：存放对象实例和数组，GC 的主战场。所有线程共享。进一步分为新生代（Eden + 两个 Survivor）和老年代。
- **方法区 / 元空间（Metaspace）**：存放类元信息、常量、静态变量。JDK 8 后从堆中移出，改用本地内存，解决了之前的 `PermGen OOM`。
- **虚拟机栈**：每个线程私有，存放栈帧（局部变量表、操作数栈、动态链接）。方法调用就是压栈，返回就是出栈。栈深度超限会 `StackOverflowError`。
- **本地方法栈**：服务于 Native 方法，行为与虚拟机栈类似。
- **程序计数器**：线程私有，记录当前执行的字节码行号，切换线程后能恢复。

> 一个常见误区：以为对象都在堆里。实际上 JIT 优化后有"逃逸分析"，未逃逸的对象可能直接在栈上分配，避免 GC 开销。

## 二、垃圾回收：谁在替你收拾烂摊子

JVM 自动管理内存，核心是**判断哪些对象该回收**和**怎么回收**。

### 2.1 判断对象存活

- **引用计数法**（基本不用）：简单但无法解决循环引用。
- **可达性分析**（主流）：从 GC Roots 出发，沿引用链遍历，不可达的对象就是垃圾。

GC Roots 包括：虚拟机栈中的局部变量、方法区中的静态变量和常量、本地方法栈中的引用等。

### 2.2 GC 算法

- **标记-清除**：标记存活，清除其余。缺点是产生碎片。
- **标记-复制**：将存活对象复制到另一块空间，清空原空间。新生代用这个，因为新生代对象朝生夕灭，存活少。
- **标记-整理**：存活对象向一端移动，清理边界外内存。老年代常用，避免碎片。
- **分代收集**：新生代用复制，老年代用整理/清除，综合性能最优。

### 2.3 常见收集器

| 收集器 | 适用区域 | 特点 |
|--------|---------|------|
| Serial | 新生代 | 单线程，适合客户端 |
| ParNew | 新生代 | Serial 多线程版，配合 CMS |
| Parallel Scavenge | 新生代 | 关注吞吐量 |
| CMS | 老年代 | 低延迟，并发标记清除，已逐步淘汰 |
| G1 | 整堆 | 分区化设计，可预测停顿，JDK 9+ 默认 |
| ZGC | 整堆 | 超低延迟（&lt;10ms），TB 级堆，JDK 11+ |
| Shenandoah | 整堆 | 与 ZGC 类似，RedHat 主导 |

选型建议：JDK 8 默认 Parallel，中低延迟用 G1；超大堆且对延迟敏感，考虑 ZGC。JDK 17 LTS 已相当成熟，ZGC 生产可用。

## 三、核心参数：调优的扳手

JVM 参数用 `-` 开头，`-XX:` 调整非稳定参数。常用的就那么几个：

```bash
# 堆大小
-Xms4g            # 初始堆
-Xmx4g            # 最大堆（建议与 Xms 相等，避免动态扩容抖动）
-Xmn1g            # 新生代大小
-XX:MetaspaceSize=256m
-XX:MaxMetaspaceSize=512m

# 新生代比例（Eden:Survivor = 8:1:1）
-XX:SurvivorRatio=8

# GC 收集器
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200    # G1 期望停顿目标

# GC 日志（JDK 9+ 用 Xlog）
-Xlog:gc*:file=gc.log:time,uptime,level,tags:filecount=10,filesize=100m

# 异常时自动 dump
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/data/dumps/
```

几个原则要记住：

- **Xms 与 Xmx 设相等**，防止堆抖动引发频繁 GC。
- **MetaspaceSize 设上限**，防止类加载失控吃光本地内存。
- **新生代别太大**，否则 Minor GC 变长；也别太小，否则对象过早晋升老年代，触发 Full GC。

## 四、调优不是玄学：一套方法论

很多人对调优的印象是"背参数、碰运气"。其实调优有章可循：

**1. 先有目标**：吞吐量优先、延迟优先，还是内存占用优先？不同目标参数走向完全不同。

**2. 先看监控再看参数**：GC 频率、停顿时间、各代增长曲线，用数据说话。Grafana + Prometheus + JVM Exporter 是常见组合。

**3. 一次只调一个变量**：否则无法归因。

**4. 回归验证**：调完用同样的压测复跑，确认收益，避免"感觉好多了"。

**5. 别过度优化**：大多数应用默认参数就够用，调优是为了解决具体问题，不是为了炫技。

## 五、实战：一次线上 Full GC 频繁的排查

> 背景：电商订单服务，JDK 8 + 4G 堆，接口偶发 2-3 秒卡顿，监控显示 Full GC 从每天 1 次飙到每小时 3 次。

排查过程：

1. **看 GC 日志**：发现 Full GC 后老年代仅回收 200M，说明老年代里有大量"顽固对象"。
2. **jmap -histo:live**：看存活对象 TopN，发现某个 `CacheEntry` 实例占了 1.2G。
3. **定位代码**：本地缓存用 `ConcurrentHashMap` 存商品信息，只进不出，没设过期和容量上限。
4. **改造**：换成 Caffeine，设 `maximumSize` 和 `expireAfterWrite`。
5. **验证**：Full GC 回到每天 0-1 次，卡顿消失。

根因往往不在 JVM，而在业务代码。调优的终点，常常是回到代码本身。

## 六、趁手的工具箱

- **jps / jstat / jmap / jstack**：JDK 自带，命令行快速排查。
- **Arthas**：阿里开源，在线热诊断神器，`dashboard`、`thread`、`watch` 一条命令看运行态。
- **MAT**：Eclipse 出品，dump 文件分析利器，查内存泄漏定位到对象引用链。
- **JFR（Java Flight Recorder）**：JDK 11+ 商业级可观测，低开销持续采集。
- **Grafana + Prometheus**：长期趋势监控，建立基线。

## 七、结语

JVM 调优不是一锤子买卖，而是一项持续工程。记住三条：

1. **默认参数通常够用**，先确认真有问题再调。
2. **监控是前提**，没有数据支撑的调优都是耍流氓。
3. **根因常在代码**，参数能缓解，不能根治设计缺陷。

把内存模型、GC 机制、调优方法论这三块吃透，再配合工具实战，你就能从容应对大多数线上问题。剩下的，交给经验积累。
