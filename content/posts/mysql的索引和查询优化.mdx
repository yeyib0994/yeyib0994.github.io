# 深入理解 MySQL 索引机制与索引优化

> 索引是 MySQL 性能优化的第一战场。理解索引不能只停留在"加个 index 就快了"，而要看清数据在 B+ 树上如何组织、查询如何走路、优化器如何选路。本文从底层结构讲到实战优化，尽量把"为什么"讲透。

## 一、为什么需要索引

没有索引时，一条查询只能**全表扫描**——从第一行逐行比对到最后一行，时间复杂度 `O(N)`。当表数据量到百万级，一次查询可能就要几百毫秒到几秒。

索引的本质是一种**有序数据结构**，它把"逐行扫描"变成"按 key 定位"，把 `O(N)` 降到 `O(log N)` 甚至 `O(1)`。

MySQL 的存储引擎层负责索引实现，不同引擎选择不同：

| 存储引擎 | 索引数据结构 | 说明 |
|---------|------------|------|
| InnoDB   | B+ 树       | 主流，本文重点 |
| MyISAM   | B+ 树       | 老引擎，索引与数据分离 |
| Memory   | Hash / B+ 树 | 默认 Hash，支持 B+ 树 |
| NDB      | Hash        | 集群场景 |

<Tip title="一句话记忆">
InnoDB 的表就是索引，索引就是表——这是理解后面所有内容的关键。
</Tip>

## 二、B+ 树：InnoDB 索引的底座

### 2.1 为什么是 B+ 树而不是其他

常见候选结构对比：

- **哈希表**：等值查询 `O(1)`，但不支持范围查询、不支持排序。
- **二叉搜索树 / 红黑树**：树高随数据量增长，磁盘 IO 次数多。
- **B 树**：每个节点既存 key 又存 data，单页能放的 key 数少，树更高。
- **B+ 树**：非叶子节点只存 key（不存 data），叶子节点存全部数据，且叶子间用双向链表串联。

B+ 树的关键优势：

1. **扇出大**：非叶子节点只存索引 key，一个 16KB 页（InnoDB 默认页大小）能放上千个 key，树高通常 3~4 层就能支撑千万级数据。
2. **范围查询高效**：定位到叶子节点后，顺着双向链表顺序扫描即可。
3. **查询稳定**：每次查询都走到叶子节点，IO 次数恒定等于树高。

<Callout type="info" title="树高与数据量的估算">
假设主键 8 字节bigint、指针 6 字节，一个非叶子页可放约 `16384 / 14 ≈ 1170` 个 key。三层 B+ 树可索引 `1170 × 1170 × 16 ≈ 2000 万` 行数据。这也是为什么大家常说"InnoDB 千万级以内性能稳定"。
</Callout>

### 2.2 页（Page）与行（Row）

InnoDB 以**页**为最小磁盘 IO 单位，默认 16KB。页内存储多行数据，页与页之间通过双向链表连接。一次 IO 哪怕只读一行，也会把整页读进 Buffer Pool。

这也是为什么"索引列占用空间越小越好"——单页能放的 key 越多，扇出越大，树越矮，IO 越少。

## 三、聚簇索引 vs 二级索引

这是 InnoDB 索引体系的核心分水岭。

### 3.1 聚簇索引（Clustered Index）

聚簇索引将**索引与数据行存储在同一棵 B+ 树的叶子节点**中。一张表只能有一个聚簇索引，默认就是**主键**。

- 如果定义了 PRIMARY KEY，用它做聚簇索引。
- 没有主键但有 UNIQUE 非空列，用它。
- 都没有，InnoDB 会自动生成一个隐藏的 6 字节 `DB_ROW_ID` 列作为聚簇 key。

叶子节点里存的是**完整的行数据**，所以聚簇索引的查找直接就能拿到整行。

### 3.2 二级索引（Secondary Index）

二级索引的叶子节点**不存整行数据**，而是存：

```
[索引列的值] → [主键值]
```

也就是说，二级索引的"值"是主键，通过主键再去聚簇索引里找完整行——这个动作叫**回表（Bookmark Lookup）**。

<Warning title="回表的代价">
一次二级索引查询 = 二级索引树查找（1 次 IO 级别定位） + 聚簇索引树查找（1 次回表）。
如果扫描大量行都走二级索引，就是成百上千次回表，可能比全表扫描还慢。这就是"索引建了但没用"的常见原因。
</Warning>

### 3.3 一个查询的完整路径

```sql
SELECT * FROM users WHERE email = 'alice@example.com';
```

假设 `email` 上有普通二级索引，执行过程：

1. 在 `email` 的 B+ 树上找到 `alice@example.com`，拿到主键 `id=42`。
2. 到聚簇索引树上按 `id=42` 定位，读取整行。
3. 返回结果。

走两棵树。如果 SQL 改成只查主键：

```sql
SELECT id FROM users WHERE email = 'alice@example.com';
```

二级索引叶子节点本身就存了主键 `id`，**无需回表**——这就是后面要讲的**覆盖索引**。

## 四、索引的几种类型

### 4.1 主键索引（PRIMARY KEY）

即聚簇索引。建表时声明 PRIMARY KEY 即可，一张表唯一。

### 4.2 唯一索引（UNIQUE）

列值必须唯一，允许 NULL（多个 NULL 在 MySQL 中视为不同值）。兼顾"约束"和"加速查询"。

### 4.3 普通索引（INDEX / KEY）

最基本的索引，无唯一约束。

### 4.4 联合索引（Composite Index）

对多列建一个索引，key 是 `(col1, col2, col3)` 的组合。这是索引优化中**最灵活、也最容易踩坑**的类型，因为受**最左前缀原则**约束（见下节）。

### 4.5 全文索引（FULLTEXT）

用于文本搜索，基于倒排索引。MyISAM 支持早，InnoDB 5.6+ 也支持。适合长文本检索，替代简单 `LIKE '%xxx%'`。

### 4.6 前缀索引

对长字符串列，只索引前 N 个字符，节省空间：

```sql
ALTER TABLE articles ADD INDEX idx_content(content(20));
```

代价是**无法用于 ORDER BY 和覆盖索引**，且前缀选择性不足时会退化。

## 五、联合索引与最左前缀原则

联合索引 `(a, b, c)` 在 B+ 树上按 `a → b → c` 顺序排列。形象理解：先按 `a` 排序，`a` 相同再按 `b` 排序，`b` 相同再按 `c` 排序。

### 5.1 最左前缀匹配

查询必须从索引最左列开始连续匹配，才能用到该联合索引：

```sql
-- 建索引：INDEX(a, b, c)

WHERE a = 1                     -- ✅ 用到 a
WHERE a = 1 AND b = 2           -- ✅ 用到 a, b
WHERE a = 1 AND b = 2 AND c = 3 -- ✅ 用到 a, b, c
WHERE b = 2                     -- ❌ 跳过了 a，无法用
WHERE b = 2 AND c = 3           -- ❌ 跳过了 a
WHERE a = 1 AND c = 3           -- ⚠️ 只用到 a，c 用不上（中间断档）
```

### 5.2 范围查询会中断后续列

一旦某列用了范围查询（`>`, `<`, `BETWEEN`, `LIKE 'x%'`），**其后所有列都无法用索引排序定位**：

```sql
WHERE a = 1 AND b > 10 AND c = 3
-- a 用到，b 用到（范围），c 用不上
```

<Tip title="优化思路">
把范围查询列尽量往后挪。把等值条件放前面、范围条件放后面，是联合索引列顺序的经典设计原则。
</Tip>

### 5.3 索引下推（ICP, Index Condition Pushdown）

MySQL 5.6 引入。在没有 ICP 之前，联合索引 `(a, b)` 上：

```sql
SELECT * FROM t WHERE a = 1 AND b LIKE '%abc';
```

引擎先用 `a=1` 定位，然后把所有匹配行**回表**，再在 Server 层过滤 `b LIKE '%abc'`。匹配行多时回表开销巨大。

开启 ICP 后，`b LIKE '%abc'` 这个条件**下推到引擎层**，在二级索引上直接判断，只对真正满足条件的行回表。回表次数大幅减少。

## 六、覆盖索引（Covering Index）

当查询所需的列**全部被某个索引覆盖**，引擎直接从索引叶子节点取数据，**不再回表**：

```sql
-- INDEX(user_id, status, created_at)

SELECT user_id, status, created_at FROM orders
WHERE user_id = 100 AND status = 'PAID';
```

`EXPLAIN` 里会看到 `Extra: Using index`，这就是覆盖索引的标志。

实战中，覆盖索引是减少回表最直接的手段。常见技巧：

- 高频查询只查几个固定字段时，为这几个字段建联合索引。
- 避免 `SELECT *`，明确列出字段，让覆盖索引有机会生效。

## 七、EXPLAIN：索引诊断的眼睛

`EXPLAIN` 是分析索引使用情况的唯一入口。重点看几个字段：

| 字段 | 关注点 |
|-----|-------|
| `type` | 访问类型，从好到坏：`system > const > eq_ref > ref > range > index > ALL`。`ALL` 即全表扫描，通常要优化 |
| `key` | 实际使用的索引。可能与你预期不同，说明优化器选了别的路 |
| `key_len` | 索引使用长度。判断联合索引用了几列 |
| `rows` | 估算扫描行数。越小越好 |
| `Extra` | `Using index`（覆盖索引）、`Using where`（Server 层过滤）、`Using temporary`（临时表）、`Using filesort`（文件排序，要警惕） |

<Tip title="type 字段速查">
- `const`：主键或唯一索引等值查询，最多 1 行。
- `eq_ref`：JOIN 中用主键/唯一索引等值匹配，最多 1 行。
- `ref`：普通索引等值匹配。
- `range`：索引范围扫描。
- `index`：扫整棵索引树（比 ALL 好，但仍是全索引扫描）。
- `ALL`：全表扫描，通常要优化。
</Tip>

## 八、索引优化实战清单

### 8.1 索引设计原则

1. **选择性高的列优先**。区分度 = `不同值数 / 总行数`，越接近 1 越值得建索引。性别这种二值列建索引意义不大。
2. **联合索引优于多个单列索引**。单列索引多了，优化器可能只选一个，或走 index merge，效率不稳定。
3. **尽量覆盖高频查询**。把 `SELECT` 常查的列纳入联合索引。
4. **索引列尽量小**。用 `int` 而非 `bigint`，用定长而非变长，单页扇出更大。
5. **外键关联列建索引**。JOIN 的连接字段必须建索引，否则会扫全表。

### 8.2 索引失效的常见场景

这些都是**建了索引但用不上**的坑：

<Warning title="六大索引失效场景">

1. **对索引列做函数/运算**

   ```sql
   WHERE YEAR(created_at) = 2026   -- ❌ 失效
   WHERE created_at >= '2026-01-01'
   ```

2. **隐式类型转换**

   `phone` 是 `varchar`，查询写成 `WHERE phone = 13800000000`（数字），MySQL 给列加函数转数字，索引失效。

3. **LIKE 以通配符开头**

   ```sql
   WHERE name LIKE '%张'   -- ❌ 失效
   WHERE name LIKE '张%'   -- ✅ 可用
   ```

   前导 `%` 无法用 B+ 树定位。全文本检索用 FULLTEXT 或 ES。

4. **OR 连接非索引列**

   ```sql
   WHERE a = 1 OR b = 2   -- 若 b 无索引，整条退化全表
   ```

   两边都有索引时可能走 index merge，但性能仍不如 UNION ALL。

5. **!= 或 **

   `WHERE status != 'PAID'` 通常不走索引（否定条件命中行多）。改用 `IN` 列举允许值，或反过来查。

6. **ORDER BY 与索引顺序不一致**

   联合索引 `(a, b)` 下 `ORDER BY b` 或 `ORDER BY a DESC, b ASC`（混排）会触发 `Using filesort`。
</Warning>



### 8.3 一个真实的慢查询优化案例

原始 SQL：

```sql
SELECT * FROM orders
WHERE user_id = 100 AND status = 'PAID' AND amount > 100
ORDER BY created_at DESC LIMIT 20;
```

假设只有 `user_id` 单列索引。问题：

- `user_id` 命中后，`status`、`amount` 都在 Server 层过滤。
- 排序触发 `Using filesort`。
- 大量回表。

优化方案——建联合索引：

```sql
ALTER TABLE orders ADD INDEX idx_user_status_created(user_id, status, created_at);
```

为什么是这个顺序？

- `user_id`：等值查询，选择性高，放第一。
- `status`：等值查询，放第二。
- `created_at`：用于 ORDER BY，避免 filesort。
- `amount > 100`：范围查询，放最后（这里它不在索引里也没关系，因为前三个已能定位+排序，`amount` 在 Server 层过滤代价小）。

再看是否需要覆盖索引。如果只查这几个字段：

```sql
SELECT user_id, status, amount, created_at FROM orders ...
```

可以把 `amount` 也加入索引尾部，变成 `(user_id, status, created_at, amount)`，实现覆盖索引，零回表。

## 九、索引不是银弹

建索引有代价，不是越多越好：

1. **写入变慢**。INSERT/UPDATE/DELETE 要同步维护所有索引树，索引越多写入越慢。
2. **空间占用**。每个索引都是一棵 B+ 树，占用磁盘和内存（Buffer Pool）。
3. **优化器选择困难**。索引多，优化器选错概率上升，可能出现"本来该走 A，却走了 B"的执行计划。

<Tip title="索引维护节奏">
- 定期用 `pt-duplicate-key-checker` 找重复索引（如 `(a,b)` 和 `(a)`，后者冗余）。
- 用 `sys.schema_unused_indexes` 找长期未使用的索引，考虑删除。
- 用慢查询日志 + EXPLAIN 定期复盘。
</Tip>

## 十、总结

把 MySQL 索引优化拆成三句话：

1. **数据在 B+ 树上按 key 有序存储**——所以等值、范围、排序都能加速，但函数运算、前导通配会破坏有序性，索引失效。
2. **InnoDB 表即聚簇索引，二级索引要回表**——所以覆盖索引、减少回表是核心优化方向。
3. **联合索引受最左前缀约束，范围查询会中断**——所以列顺序设计要"等值在前、范围在后、排序字段靠后"。

真正的优化不在背规则，而在用 EXPLAIN 看清每条 SQL 实际怎么走、回了几次表、扫了多少行。规则是地图，EXPLAIN 是脚下的路。
